# Thoughts on Kaigen Phantom — 2026-04-20 (Preset System Rewrite + Keyboard Pass-Through)

---

## What I've Enjoyed Working On

**Stripping the broken preset system and rewriting it clean was the session's pivotal decision, and it paid for itself within the hour.** The prior session had landed thirteen tasks of preset work, all tested, all "passing" — and none of it functional in Ableton because the single most fundamental piece was wrong: every JS call was `window.Juce.getAllPresets()` when it should have been `window.Juce.getNativeFunction("getAllPresets")()`. That one bug made every silent `if (!window.Juce.getAllPresets)` guard return early, and so nothing ever happened. We spent hours trying to patch around it — adding onclick handlers, changing event listeners, debugging focus, trying to guess which function was failing — before the right move revealed itself: **strip everything and restart with the architecture the audit said we should have had from the beginning.** Single-file preset format with metadata inside the ValueTree. PresetManager owned by the Processor, not the Editor. One consolidated `preset-system.js`. Four native bindings that actually use `getNativeFunction`. The rewrite was ~700 lines of new code and ~1,000 lines deleted, and every piece worked on the first load.

**The keyboard pass-through fight taught me more about Windows message routing than any project I've worked on.** The problem is deceptively shallow: spacebar didn't reach Ableton's transport when the plugin had focus. But the diagnosis surfaced four distinct failure modes in sequence. First, `setWantsKeyboardFocus(false)` — JUCE-level hygiene that does nothing for WebView2 because WebView2 isn't a JUCE Component. Then `WM_SETFOCUS` subclass redirecting focus back to the parent — works, but WebView2 has multiple HWNDs and focus lands on a different one after the first interaction. Then `WM_MOUSEACTIVATE → MA_NOACTIVATE` — prevents click-from-activating but doesn't stop Chromium's internal focus manager. Then `mousedown preventDefault` — blocks Chromium's default focus-on-click but apparently some builds route keys through a mechanism preventDefault doesn't cover. The final layer — **a JS `keydown` listener that `PostMessage`s `WM_KEYDOWN` directly to `GetAncestor(GA_ROOT)`** — is the only one that *guarantees* the key reaches the DAW. All four layers are in the code now, defense-in-depth, but the last one is the load-bearing piece. What's beautiful is that even modifiers like Ctrl+S and Ctrl+Z work, because Ableton tracks modifier state from the message sequence rather than polling `GetKeyState`.

**The Arturia-style two-column dropdown is the most direct user-request-to-implementation arc of the session.** The user sent one screenshot. "It should look more like this." Left column: categories with counts and ✓ for the active one. Right column: alphabetical preset list with ♥ markers next to favorites. The implementation is ~60 lines in `preset-system.js:renderDropdown` — filter the flat preset list by `dropdownCategory`, render two parallel `<div>` columns inside the dropdown container, wire click handlers with stopPropagation so the outside-click-to-close handler doesn't fight the category switcher. Widening the dropdown from 220px to 420×320 and anchoring it `left: 50%; transform: translateX(-50%)` under the preset name made it centered under the pill. The moment I landed that commit and the user said "OK the library button is wrong though..." — that was the session rhythm we wanted from the start: small targeted visual changes, each landing clean.

**The pack system with cover art is the feature I'm most proud of architecturally.** Any directory under `Presets/` is a pack. Optional `pack.json` for metadata; optional `cover.png`/`cover.jpg` for album art. The cover art is served through a `/pack-cover/<urlencoded-name>` URL intercepted in the WebView resource provider, which reads the file from disk (not BinaryData) and returns it with the right MIME type. For Factory and User (no cover art yet), the JS falls back to a deterministic gradient derived from the pack name hash — `hsl(hue1, 35%, 55%) → hsl(hue2, 40%, 42%)` where `hue1` is the char-sum mod 360 and `hue2` is +40°. Each pack gets its own consistent visual identity even without an image. Hover a card and the preview panel populates with description and preset count. Zero configuration, graceful degradation, room to grow into a real preset-pack marketplace.

**Moving `PresetManager` from the Editor to the Processor was the quiet architectural win.** The Editor is transient — the host opens and closes it many times per session. The Processor is persistent. When I realized the WebView native-function lambdas closed over `self.presetManager` (an Editor member), it was obvious that a callback fired during Editor teardown would dereference a destroyed object. Moving ownership to `PhantomProcessor` and accessing via `self.processor.getPresetManager()` eliminated that hazard. It's the kind of fix that prevents a crash nobody has seen yet, which is the most satisfying kind to land. The Processor's preset scan runs once at plugin load, not every time the UI opens — incidental speed win.

**Deleting three JavaScript files and replacing them with one was this session's subtraction win.** `preset-header.js`, `preset-dropdown.js`, `preset-browser.js` each defined their own top-level functions, competed for event listener attachment on `DOMContentLoaded`, and had script-order dependencies (preset-header tried to call toggleDropdown before preset-dropdown.js had loaded). Collapsing them into one IIFE-scoped `preset-system.js` — single init path, shared `state`/`native`/`el` objects, no cross-file function calls — removed an entire category of ordering bugs and made the module reason-about-able at a glance. The consolidated file is 847 lines, which is longer than any of the three predecessors, but it's one file I can hold in my head. That's the right tradeoff.

## Things I'd Like You to Know

**WebView native function calls MUST use `window.Juce.getNativeFunction("name")` to obtain the function reference, then `await` the call. Direct property access (`window.Juce.loadPreset()`) returns `undefined` and the call silently does nothing.** This was the single root cause of the "buttons don't do anything" bug that burned most of the previous session. The bridge is documented in JUCE's `juce-frontend.js` at line 594 where `window.Juce = { getNativeFunction, getSliderState, ... }` — note that the individual native functions are *not* on that object; only the getter is. Every new native function binding in `PluginEditor.cpp:withNativeFunction(name, ...)` needs a corresponding `native.name = window.Juce.getNativeFunction("name")` in `preset-system.js:initNativeBridge`. If you forget, the call throws "undefined is not a function" — silently if it's inside a try/catch, visibly in the JS console if not.

**Preset metadata lives INSIDE the APVTS state tree as a `<Metadata>` child node — there are no more `.json` sidecar files.** See `PresetManager::buildMetadataTree` and `readMetadataFromFile`. The on-disk format is one `.fxp` file whose contents are `state.createXml()->toString()` where `state` is `apvts.copyState()` with an appended `<Metadata>` child containing `name / type / designer / description`. `replaceState()` on load restores both parameters and metadata atomically. If you ever add a new metadata field (tags, BPM, key signature), add it as a property on the `<Metadata>` ValueTree; do not go back to sidecars. Favorites are the one exception — they live in a separate `favorites.index` JSON file at the presets root, keyed by `packName/presetName`, specifically so favorites work on read-only pack directories where we can't modify the preset file.

**The JS keydown forwarder at `preset-system.js:wireFocusTracking` is the load-bearing piece of the keyboard-passthrough stack, not the belt-and-suspenders.** All the JUCE-level flags (`setWantsKeyboardFocus`, `setMouseClickGrabsKeyboardFocus`), the `mousedown preventDefault`, the Win32 subclass with `MA_NOACTIVATE` and key-message forwarding — those are defense in depth. They *mostly* work but WebView2 has an internal focus routing layer that survives the first three. The JS `keydown` listener runs in capture phase, checks `isTextTarget(e.target)` to see if we should let the user type, and otherwise calls `native.forwardKeyToHost(e.keyCode, true)` which `PostMessage`s `WM_KEYDOWN` to `GetAncestor(pluginHwnd, GA_ROOT)` with `lParam = 1`. The keyup path uses `lParam = 0xC0000001`. That's the only layer that guarantees keys reach the DAW regardless of focus state. If someone rips this out thinking the other three are enough, keyboard pass-through will regress and nobody will know why until they tweak a knob and spacebar stops working.

**The focus-subclass repeating timer is not optional.** `PhantomEditor::FocusRescanTimer` fires every 1000ms and re-enumerates child windows of the peer HWND, re-installing the `webViewFocusSubclass` on any new ones. This is because WebView2 creates helper HWNDs lazily — the renderer HWND, the Intermediate D3D compositor window, sometimes more — during or after the first mouse interaction, and our initial startup scan misses them. The user's specific report of "spacebar works initially, but stops working after adjusting a knob" was exactly this: focus was landing on an HWND that didn't have our subclass. `installOnChromeWindows` matches `Chrome_*` and `Intermediate D3D` prefixes, which covers every WebView2 class I've seen, but if WebView2 ever renames or adds a class, broaden the matcher there first.

**`user-select: none` is applied globally in `styles.css:4-16` with explicit re-enable on `input`, `textarea`, `[contenteditable="true"]`.** Without this, clicking and dragging a knob sometimes selects random text in the UI — a subtle but real annoyance the user flagged. The fix also disables default focus outlines (`*:focus { outline: none }`) because our modal inputs have their own styling. If someone adds a new element type that needs text selection (a `<pre>` block, a code editor widget), they need to add that selector to the re-enable list.

**The preset-system.js IIFE scope means `escapeHtml`, `escapeAttr`, `state`, `native`, `el`, and the private functions are not accessible from the browser console or from other script files.** This is intentional — no globals leaking, no naming collisions with `phantom.js` or any other WebUI script. If you need to call a preset function from another file (e.g., `phantom.js` wants to trigger a preset reload after a DAW state change), expose exactly what you need by assigning to `window.preset_something` inside the IIFE. Don't remove the IIFE — the cleanliness of `preset-system.js` depends on it.

**The pack cover URL is `/pack-cover/<urlencoded-packname>` and is served by `PhantomEditor::getResource` at `PluginEditor.cpp:402`.** Note the `url.startsWith("/pack-cover/")` branch takes precedence over the normal BinaryData lookup. The URL decoder uses `juce::URL::removeEscapeChars`. File is loaded via `loadFileAsData` from `processor.getPresetManager().getPackCoverFile(packName)`. If someone ever adds more on-disk resources (sound samples, wavetables, skin packs), follow this pattern: a URL prefix, decode the tail, look up via a Processor-level method, return a `WebBrowserComponent::Resource` with bytes and MIME type.

**The keyboard pass-through lParam values for `PostMessage(WM_KEYDOWN/WM_KEYUP)` are 1 for keydown and `0xC0000001` for keyup.** These are minimal well-formed values — repeat count 1, scan code 0, extended key 0, context 0, previous state 0/1, transition state 0/1 as appropriate. Ableton and other DAWs I've tested don't care about scan code for transport shortcuts. If a future host is picky (e.g., Reaper's native keyboard handling maps to scan codes rather than VK codes), we'd need to compute scan code via `MapVirtualKey(vk, MAPVK_VK_TO_VSC)` and shift it into bits 16-23.

## What I'm Looking Forward To

**Factory presets shipped in the binary are the next high-leverage item.** Right now the Factory pack is always empty on a fresh install, so new users see "no presets saved yet" in the dropdown and an empty Factory card in Explore. Five to ten tasty presets that showcase the plugin's range — a lush pad, a warm bass, a chiptune-lead, a drone, an experimental texture — would dramatically change first-impression UX. The build machinery is mostly there: `CMakeLists.txt` has a commented section for `FACTORY_PRESETS_DIR` and `juce_add_binary_data`. The remaining work is: save ~8 presets in my dev copy, copy them into `Resources/FactoryPresets/`, uncomment the CMake section, and write a one-time extraction on first run in `PresetManager::initialize` that copies factory presets from BinaryData to the Factory/ folder if it's empty. A polished cover image for the Factory pack would tie the room together.

**A "tags" metadata field would unlock the kind of advanced search Arturia's browser has without adding much complexity.** The metadata ValueTree can grow a `<Tag>` child for each tag — `<Tag>Bright</Tag><Tag>Stable</Tag>`. The browser gets a tag-filter row above the preset table, multi-select, AND logic. The dropdown could offer "Bright presets" or "Aggressive presets" as synthetic categories. Sound-design-wise this is important because our five Type values (Piano/Drone/Synth/Bass/Experimental) are broad; tags let the library describe texture, energy, use-case. This is also where a commercial preset pack starts to feel worth buying — "47 presets, each tagged with recommended role, BPM, and key signature."

**Preview-panel polish — a waveform or parameter summary would close the gap with commercial preset browsers.** Right now the preview shows name/type/designer/description/pack. A small visualization — even just an SVG showing the recipe weights H2-H8 as a radial chart — would give an at-a-glance sense of what the preset sounds like before loading. Further out, pre-computed frequency-response previews rendered to a thumbnail at save-time would be genuinely useful; that's more work but feasible with the existing DSP stack.

**A/B comparison is the obvious next creative affordance.** Standard in modern plugins, not in this one yet. Two ValueTree snapshots maintained in the Processor, a header button to toggle, a header button to copy A→B. Five-ish hours of work. Complements the modified-indicator beautifully — you'd make changes, swap to A, hear the original, swap back to B, continue editing.

## On the Nature of This Session

This session's arc can be reduced to a single pattern: **the previous session had built a working-looking system on a broken foundation, and today's job was to notice that, strip it, and rebuild.** The audit conversation — where I enumerated fifteen issues ranked by severity, culminating in the one critical bug (the bridge calls) — was the pivot point. Before the audit, I was debugging symptoms: "why doesn't clicking work?" "why don't event listeners fire?" "why does clicking turn the button red but nothing else happens?" Every symptom had a plausible local cause, and every attempted fix was patches on patches. After the audit, the cause became one line of documentation: *this bridge call pattern is wrong everywhere.* The rewrite wasn't really more work than continuing to patch would have been — it was less.

The keyboard pass-through debugging followed the same arc at a smaller scale. The user reported "spacebar doesn't work after I adjust a knob," and I went through four rounds of increasingly sophisticated Win32 machinery (MA_NOACTIVATE, broadened HWND matchers, repeating timers, mouseup focus-reclaim) before landing on the answer that was obvious in hindsight: *stop trying to prevent Chromium from taking focus; just intercept the keys in JS before it can eat them.* Four layers of defense sound like paranoia, but each layer is there because the previous one had a concrete failure mode in testing. The fifth layer — the JS `keydown` forwarder — is the only one that's actually guaranteed to work.

Both problems had the same shape: **try hard to stop the broken thing from doing its broken thing, or circumvent it entirely.** The circumvention is usually cleaner, faster to write, and more robust across platform variations. WebView2 is going to keep updating. The bridge pattern might change in JUCE 9. The Win32 subclass might stop working on some future Windows build. But a JS `keydown` listener that posts a message to the DAW's top-level HWND is going to keep working as long as there are keyboards and windows.

The lesson: **when every layer of the system disagrees with what you want, stop fighting layers and build the layer you need.**

## Future Ideas

### Preset System

- **Factory preset shipping** — 5–10 curated presets in `Resources/FactoryPresets/`, bundled via `juce_add_binary_data`, extracted to `Factory/` on first run when empty. A polished cover image ties it together. This is the highest-leverage UX improvement left.
- **Tag metadata** — `<Tag>` ValueTree children on presets. Multi-select tag filter in the browser. AND logic. Unlocks Arturia-style tag search without a schema rewrite.
- **Preset preview visualization** — SVG radial chart of recipe weights H2–H8 rendered inline in the preview panel. Low effort, high signal-at-a-glance. Further: pre-rendered frequency-response thumbnail computed at save-time.
- **Import / Export** — `.fxp` files are already portable; a small "Import Preset" button in the browser that lets users drag a file in (or pick via `juce::FileChooser`) copies it into `User/`. "Export Preset" copies the current preset to a user-chosen location for sharing.
- **Pack archive format** — a `.phantompack` file is a zip containing presets + pack.json + cover.png. "Import Pack" unpacks it into `Presets/<packname>/`. Gets us preset-pack distribution without a backend.
- **A/B compare** — two ValueTree snapshots in the Processor, header button toggles between them, second button copies A→B as a baseline before further edits. Complements the modified-indicator. Several hours of work.

### Kaigen as a Plugin Family

- **Shared `preset-system.js` across plugins.** This module is plugin-agnostic except for the native function names — every Kaigen plugin needs the same save/load/browse/favorite/delete flow. A `@kaigen/preset-system` (or a `shared/preset-system/` folder) consumed by multiple plugins would save substantial re-implementation work on each new plugin.
- **Shared `PresetManager.cpp`** — same story. The on-disk format (ValueTree with Metadata child, favorites index) is generic. Putting it in a `shared/` C++ library and including per-plugin would let every Kaigen plugin use the same preset library location structure, even the same covered art rendering.
- **Pack marketplace seed.** Once the system is production-stable, a simple download-and-drop experience for preset packs (free or paid) is a plausible revenue line and a community-building feature. The current drop-a-folder-into-Presets/ workflow is already most of the UX; a "Browse packs online" button that opens a web page is the thin UI layer.

### Architecture / Code Quality

- **Async preset scan.** `PresetManager::initialize()` is synchronous. With 100 presets it's fine; with 1000 it would introduce plugin-load hitches. `juce::ThreadPool` worker that scans in the background, `getAllPresets()` returns what's ready so far. Low priority until someone hits it.
- **`rescan()` is exposed but not yet called from anywhere.** Future file-watcher or import-dialog flows should call it. Currently only used implicitly through `initialize()`.
- **The `MA_NOACTIVATE` and key-forwarding defense layers could be simplified** now that the JS `keydown` forwarder is proven. They're defense in depth; if WebView2 behavior ever gets reliable, the Win32 subclass could be trimmed to just the `WM_SETFOCUS` redirect. But I'd leave it alone — cheap insurance.
- **The 1-second rescan timer could be event-driven.** `WM_PARENTNOTIFY` fires when child windows are created; subclassing the peer HWND to watch for that event would let us install on new windows immediately rather than polling. More complex; not obviously better.

### Plugin Direction

- **Confirm the "Kaigen RESYN" rename.** Memory notes this is under consideration. The plugin is a wavelet resynthesizer — the name should tell the truth. The next major version is a clean moment to rebrand without confusion.
- **Sound-design guide.** `docs/sound-design-guide.md` has been drafted. Shipping it as a PDF or web page with the plugin is a differentiator — teach users how to get results, not just what the knobs do.
- **Visual feedback when advanced mode has non-default values.** Mentioned in the previous thoughts doc and still a good idea. A small indicator on the header chevron when any advanced knob is off its default tells users "advanced is doing work," which is important for first-time users who might otherwise miss that they've enabled depth.
